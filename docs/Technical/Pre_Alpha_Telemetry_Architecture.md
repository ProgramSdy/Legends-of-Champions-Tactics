Batch B was approved, implemented and independently reviewed locally; [implementation evidence](../Codex/Stage_5_3_Batch_B_Implementation_Report.md) awaits Owner acceptance. This is **not deployed RELEASE-004 behavior**. Public collection, live migration and deployment await separate approval.

## Boundary and P0 scope

Use the existing Public SQLite identity and battle lifecycle as the source of truth. Capture first-party visitor/source, meaningful 30-minute analytics sessions, home observation, authoritative battle activation/terminal facts, immutable launch rosters and available-hero snapshot, UTC cohorts, separate API/battle/client reliability, and restricted exports. Explicitly exclude internal test accounts. A single, non-intrusive **external Feedback & Bug Report link** belongs in the existing Game Manual menu, available from Stage Map and Battle; the external URL and channel are prepared in Stage 6. There are **no** in-game surveys, feedback popups, text forms, feedback API, feedback table, dashboard, or P2 features in Stage 5.3. P1 skill/status summaries and optional coarse device information remain deferred unless separately approved as cheap after P0.

Public telemetry capture must be **disabled by default** through an explicit release gate until the privacy notice, consent applicability, retention/deletion policy, access controls, external link destination and launch requirements are approved and validated. Deployment of dormant schema/code is not permission to enable collection. A missing link URL must not create a broken button; final destination approval is a Stage 6/Owner dependency.

## Minimal additive storage and logical event contract

The local implementation retains Public schema v5/battle revision 2 and adds a distinct `telemetry_schema_revision=1` marker after an explicit backup-first offline upgrade. A disposable-copy rehearsal with unmodified RELEASE-004 source proved old-code schema, identity and save-slot compatibility. Only telemetry-owned tables/indexes are added; player identity, save progress and battle outcomes are not duplicated.

| Proposed record | Minimum fields and authority |
|---|---|
| `telemetry_visitors` | Random browser `visitor_id` (not a fingerprint), first observed UTC time, allowlisted first-touch source and bounded campaign, linked player ID only when authenticated linkage is observed. Browser count is not a person count. |
| `telemetry_sessions` | Opaque analytics session UUID, visitor/player IDs where known, started/last meaningful activity UTC, last session source, environment/build. End after 30 minutes of inactivity. Existing 30-day `player_sessions` remain authentication credentials and must not be used as engagement sessions. |
| `telemetry_battles` | One row keyed by existing `battle_id`: post-activation UTC time, stable encounter/mode/stage, optional attempt ID, ordered player/enemy hero IDs and formations/slots, available unlocked hero IDs, control mode, build/ruleset, completed rounds if captured. This stores facts absent from `battle_diagnostics`, not another outcome column. A start row is written only after `activate_public_battle` succeeds. |
| `telemetry_events` | Bounded allowlisted UI observations (`landing_view`, `home_view`, throttled meaningful activity only when needed, sanitized `client_error`) with UUID event ID, schema version, server receipt UTC, optional occurred-at UTC, nullable visitor/player/session/battle IDs, producer, environment/build and validated payload. Uniqueness rejects duplicates; unsupported types are rejected. |
| `telemetry_internal_accounts` | Explicit exact `player_id` exclusions for load-test, owner-test and automation accounts, operator-reviewed and time-stamped. No display-name/UUID-prefix inference. A restricted offline `classify-internal` command validates the exact existing player ID, is idempotent and refuses silent relabeling; removing a classification requires a separate Owner-reviewed correction because it would alter prior cohort reports. Unknown historical classifications remain a data-quality gap. |
| `telemetry_api_metrics` and operational counters | Bounded per-minute route-template/status/latency histograms, with HTTP 4xx/5xx/exception failure counts; no per-request SQLite row. Normal shutdown performs a bounded best-effort flush. Process-local sanitized drop counters are not durable; host CPU/RAM, SQLite contention and lease sampling remain Batch C performance-validation work. |

Logical `identity_created` comes from the existing `players.created_at`; `battle_ended`/`battle_abandoned` and reason come from existing authoritative `battle_diagnostics`/`battle_settlements`. `battle_started` is the successful activation plus `telemetry_battles` row, never a provisional reservation. Export may project stable UUID event IDs from canonical IDs/type; if physical event records are chosen, uniqueness and the failure rules below still apply. Retry, second battle and team switching are derived queries, not duplicate counters. Never persist Recovery Codes, session/CSRF tokens, raw IPs, full referrers, arbitrary query strings or unsanitized stack traces in telemetry.

The external feedback link is navigation, not `feedback_submitted`; no game-owned feedback event or storage exists. Its shared Game Manual integration is implemented; a missing or invalid URL hides it. A valid configured HTTPS destination opens in a new tab with `noopener noreferrer`. The final destination remains an Owner/Stage 6 decision.

## Exact KPI interpretation

Implement the Marketing plan's denominator/window definitions without inventing historical events: First Battle Start Rate uses eligible **new players** starting within seven days of identity creation; First Battle Completion Rate uses eligible first starters and a valid gameplay outcome, with abandon/error/unknown separate; Second Battle Start Rate uses eligible first-battle completers starting again within seven days of completion; Retry After Defeat uses the same player and encounter within 24 hours of a defeated attempt. D1/D7 count **battle starts** on UTC calendar day +1/+7 after first battle start, only for cohorts with a full observation day. Composition diversity uses unordered hero-ID multisets with slots separate; Team Switching compares adjacent eligible battle pairs for the same player/mode, with formation-only changes separate. Zero denominator is N/A. Report API failure requests / all API requests, battle errors / activated starts and client-error sessions / observed sessions as **separate rates**, with numerator/denominator and data completeness visible. HTTP 4xx/5xx and uncaught exceptions count as failed API requests; route/status buckets preserve their distinction. This API rate is service-wide, including internal traffic, because anonymous/request aggregates cannot reliably exclude internal accounts; player/session/battle KPIs exclude exact classified IDs. Do not infer missing RELEASE-004 telemetry.

## Transaction and failure isolation

Identity creation, battle activation/settlement, rewards and save writes must remain on their existing authoritative transaction path. Telemetry is a **post-commit, best-effort side effect** or a projection of already-committed canonical rows, never a required write inside the gameplay transaction. Specifically: `players.created_at` and canonical terminal state require no telemetry write; after successful battle activation, try one idempotent `telemetry_battles` insert; after successful settlement, try an idempotent rounds update if available. No telemetry exception is propagated to the gameplay response, no telemetry lock is held around engine work, and a telemetry endpoint is not called synchronously before an authoritative commit. Bounded noncritical writes get short timeouts, no unbounded retries and a sanitized drop/failure counter. A crash between commit and telemetry insert leaves an observable missing measurement; a bounded local reconciliation from **canonical** records may restore only facts that actually exist, never fabricate roster/session/visitor data. Report missing-capture rates and stop launch if completeness is inadequate.

This separation trades perfect completeness for the non-negotiable rule that telemetry cannot block player identity, battle settlement, reward delivery or save persistence. It also avoids a duplicate independently committed outcome record. The remaining risk is lost sidecar facts after crash or SQLite contention; Batch C must quantify it. If a proposed schema change would force telemetry constraints into an existing critical transaction, reject that design and keep the sidecar/projection boundary.

## Privacy, volume, export and release compatibility

Use a first-party random visitor ID and only an allowlisted source (`itch.io`, `reddit`, `x`, `threads`, `taptap`, `direct`, `other`, `unknown`) plus bounded campaign. Normalize or drop unknown values. Cap client event bodies, event types and rate; one landing/home event per analytics session, meaningful activity updates no faster than every five minutes, and a small per-session cap on client errors. A bounded queue drops low-priority observations rather than delaying gameplay. The 90-day raw retention is a **provisional planning assumption**, not an approved Public policy. Deletion must be transactional and incremental by UTC cutoff, preserve canonical player/save/battle data, account for WAL/index space and log the deletion count without identifiers. Restricted offline CSV/SQL export requires an explicitly allowlisted Unix operator UID, private output directory, allowlisted columns/query templates and mode-0600 output outside the repository; it omits credentials/free text and never exposes an HTTP export endpoint. Operator activity is controlled by host access policy; a durable per-invocation audit log is not yet implemented and remains a Batch C operational decision. No public dashboard.

For a conservative sizing illustration, assume **100 daily players × 2 analytics sessions/day × at most 6 compact rows/session × 90 days = 108,000 rows**. At a measured future 0.5–1.5 KiB per row including indexes, that is ~53–158 MiB before snapshot/WAL copies; three retained copies could need ~160–475 MiB. At 500 daily players, multiply by five (~0.26–0.79 GiB primary, up to ~2.4 GiB with three copies). Battle snapshots and logs add more. These are scenario calculations, **not measured traffic or a storage guarantee**. The Stage 5.2 report's last observed ~2.3 GiB free is historical; remeasure before any deployment, monitor actual bytes/row and stop on insufficient disk margin. Do not claim 200-battle capacity from the configured limit.

Use the accepted Stage 4 evidence as the performance baseline: a bounded 10-player 3-RPS run, 20-player run and final 30-player/30-settlement run. The final 30-player run reached 30 observed concurrent leases, 2.97 battle RPS and battle-request P95 ~1,090 ms, but ended before a 300-second endurance window; [Stage 4 report](../Codex/Stage_4_2_1_Implementation_Report.md) records the limits. Batch C repeats only a justified, authorized comparable test with telemetry enabled, measuring p50/p95, CPU/RAM, SQLite busy time, WAL/disk growth, dropped events and battle settlement completeness against that baseline—not a maximum-capacity claim.

Public runtime refuses implicit migration. Back up first and run an **explicit offline additive migration on an isolated copy**. Prove both new code and unmodified `RELEASE-004-fe332708` can open/use a migrated copy, including representative player/save/battle operations and SQLite integrity/foreign-key checks; merely observing that its validator uses subset checks is insufficient. Preserve the established Single-Release strategy: rollback means reinstall the verified local RELEASE-004 archive while preserving the live database and all post-upgrade player progress. Never roll back by overwriting live data with a stale pre-migration backup. If old-code compatibility fails, Batch C stops for a new Owner-approved rollback design.
