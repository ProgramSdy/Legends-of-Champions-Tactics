This plan is based on the Owner's Human Playtest brief; the current GDD, architecture, web UI, battle contract, RELEASE-001 isolation report, Stage 4 report and deployment runbook; and a read-only source inspection. Important starting points:

- `docs/GDD/Hero_System.md`, `Game_Design_Document.md` and `Combat_System.md` still describe repeated player definitions as valid. **That historical baseline conflicts with the new Owner-approved BUG-001 requirement.** Implementation must deliberately update these authoritative rules after the new behavior is verified; do not leave conflicting GDD statements.
- `battle_api/adapter.py` publishes stable definition IDs such as `hero.warrior.weapon_master`, while battle-local combatant IDs and runtime names identify instances. `web-ui/components/battle/TeamBuilder.tsx` uses definition IDs for player slots; its visible matrix currently reserves an already-chosen definition only for another **Arena** slot. `battle_api/models.py` accepts player-team arrays for generic, Stage and Arena creation without a duplicate-profession check at the model boundary. The canonical equality key still needs confirmation against the complete roster and persistence paths.
- `web-ui/components/battle/StatusIcon.tsx` renders an in-place tooltip; `web-ui/app/globals.css` positions it with a fixed `190px` width and `left: 0`. The target preview in `BattleScreen.tsx` is absolutely positioned above its figure with a fixed offset. These are likely overflow surfaces, not a complete popup inventory.
- `web-ui/lib/battle/presentationConfig.ts` currently defines **monitor, laptop-large, laptop-medium, pad, pad-mini, phone, and portrait** presentation modes. Portrait is a rotate-device state, not the normal battle layout. BUG-002 must be checked in **every mode**, including orientation/resize transitions, not merely a desktop/mobile pair.
- `BattleScreen.tsx` owns a local `autoBattle` checkbox state in the shared Battle UI; the observed source uses it to suppress target preview but shows no player-action execution path from that toggle. `battle_api/adapter.py` already resolves computer-controlled actions using specialization AI and a legal-action repair path; Stage Learner enemies use a different random legal-action policy. The player's requested “applicable Tactics Level” needs an explicit mapping to the existing Stage/Arena/Debug mode semantics before code changes.
- RELEASE-001 uses explicit `LOCT_RELEASE_MODE`; Public frontend builds omit `/debug` and `/assets` before route discovery, and the Public backend does not register Debug creation. Shared Battle components remain in the Public artifact. Therefore hiding the toggle alone is insufficient if a reachable Public API can activate player-side AI.

These are planning observations, not a completed root-cause audit or verification that any proposed code change works.

## Confirmed bugs and acceptance requirements

### BUG-001 — Duplicate Hero Selection

One **player** team must not contain the same Hero Profession twice. Two Warrior Weapon Masters are invalid; Warrior Weapon Master plus Warrior Defence is valid. The same profession may occur on opposite teams. Confirm whether the stable definition ID is exactly the profession key for all approved heroes and future aliases; never use battle-local combatant ID, display name, or faculty alone as uniqueness authority. Prevent duplicate selection in every player team builder and reject crafted direct requests through the authoritative launch/validation paths, including Stage, Arena, and Development generic/Debug where those permit player-team choice. Preserve enemy generation, enemy-side overlap, summons, and all unrelated rules. A saved invalid composition must be surfaced for correction at selection/launch, not silently deleted or rewritten; identify any persistent team/squad data and determine whether six-hero Arena squad rules need a compatible repair path before changing its storage.

Acceptance: no duplicate-profession player team in 1v1/2v2/3v3; disabled/clearly explained already-selected cards remain keyboard-accessible as information; replacement/unselection works; direct API duplicates fail with a stable typed validation response; same-faculty/different-specialization and cross-side matches pass; existing valid saves and progression remain unchanged. Include positive, negative, boundary, direct-API and saved-data regression tests.

### BUG-002 — Battle popup overflow, **all viewport types**

Fix the enemy-card debuff tooltip extending past the right viewport edge and the target damage/hit preview extending above the top edge. Audit friendly/enemy buff/debuff status icons, Hero Stats, skill descriptions, target/self previews, turn-order names, and other contextual Battle overlays. Prefer a shared viewport-aware positioning primitive where it reduces duplicated bugs, but preserve each surface's appropriate semantics. It should flip/shift and constrain width/height to the actual visible viewport, recalculate after resize/scroll/content changes, avoid clipping/hidden stacking contexts and important controls, retain hover **and keyboard focus** behavior, and keep information/content/style intact. If a portal is needed, preserve accessible association and battle layering.

**Mandatory viewport matrix:** browser-verify the two confirmed bugs and representative popup inventory at **monitor, laptop-large, laptop-medium, pad, pad-mini, phone, and portrait** modes defined by `battlePresentationConfigFor`. For each landscape mode use at least one representative size and boundary-adjacent size where practical; test the rightmost enemy card, leftmost friendly card, topmost battle target, lower-edge status/skill controls, long tooltip content, zoom where feasible, and resize/orientation transitions. Portrait should show the intended rotate-device state without an escaped or stranded popup; do not claim its normal battle layout was tested if it is unavailable. Capture actual browser screenshots or equivalent visual evidence plus bounding-rectangle assertions with a small edge margin. Unit tests alone do not satisfy acceptance. Check pointer and focus activation, no unintended hit-target obstruction, and no horizontal/vertical page overflow caused by the popup.

### BUG-003 — Auto Battle and Engineering isolation

In explicit Development Engineering Test & Debugging mode, enabling Auto Battle should make **player-controlled** heroes act through the existing Python AI at their applicable Tactics Level. Disabling it returns manual control at a safe action boundary. Define a single in-flight-action policy: an already accepted action finishes; no new automatic player action begins after disable is acknowledged. Stop on battle end, departure, error/revocation, or settlement; prevent overlapping loops, duplicate commands, stale revisions, illegal target/skill selection, and action after terminal state. Reuse the engine's AI/legality and server authority rather than reimplementing decisions in React. Enemy AI and normal gameplay must not change.

The toggle is available only in intended Engineering UI, never ordinary Development Stage/Arena or Public Battle UI. Public build/route and server gate must make player-side auto action unreachable even through crafted direct API requests; test route absence/OpenAPI and direct calls, not visibility alone. Preserve RELEASE-001 `/debug` and `/assets` exclusions and normal player command/preview/settlement behavior. Specify whether “Tactics Level” is the existing Stage `learner`/`tactics` distinction, a hero-specific AI setting, or a new Debug control **before** implementation; do not invent a new public gameplay system. Test enable/disable during manual turn, during in-flight resolution, while enemy/forced actions run, after settlement, on navigation, and across refresh/reconnect where supported.

## Production deployment and rollback validation — **plan, not authorization**

1. With Owner-approved maintenance window, record `current` target, running commit/build, service/health baseline, DB schema/integrity, available disk/memory, backup freshness, active battles, and agreed interruption/downtime notice. Do not strand active battles; define drain/expiration/resign policy without granting unfinished rewards.
2. Under the Single-Release Strategy, create a **temporary verified recoverable copy** of the currently deployed application release before replacement, with hashes, permissions and sufficient free disk. It need not be retained as a standing second release after validation. Test on an isolated copy that the old artifact can start against the expected unchanged schema. If the old artifact, dependencies, secrets/configuration or disk space cannot be preserved, stop; a symlink switch alone is not a rollback plan.
3. Take/verify a consistent pre-release SQLite backup and protected copy of the current environment configuration; record immutable hashes/locations and restore access. Never place secrets in the release manifest or logs. Do not restore an older database over newer player data solely to roll back application code.
4. Deploy the new candidate via the actual installed service/release layout, keeping durable DB and `/etc/loct/public.env` outside replaceable artifacts. Verify API health, frontend, entry, existing-player session/save loading, representative core battle/receipt/progression, Public Debug/Auto Battle isolation, and no unintended config drift. Use designated test identities only; record any persistent test writes.
5. Perform the **actual application rollback** to the saved previous artifact using the rehearsed Single-Release-compatible procedure. Verify old API/Web start, health, old code's compatibility with **current preserved player data**, save loading and core gameplay, and the absence of Public Engineering features. If data/schema compatibility fails, stop; do not conceal it with DB restore.
6. Redeploy the new candidate, repeat health, save/gameplay, isolation and data-preservation checks, then remove temporary old-artifact material only after successful verification and according to the approved Single-Release policy. Record exact times, downtime, health/rollback outcomes, preserved data checks, service/DB state and unresolved incidents in the implementation report and canonical deployment runbook.

Execution must account for e2-micro disk headroom and local-only backups, process memory, SQLite write quiescence, active RAM-only battles, Nginx/systemd behavior, and failure recovery. Do not invent installed commands from repository templates. The current public domain, cloud firewall or paid infrastructure is not to be changed by this plan. A failed rollback drill is a failed release gate, not a documentation success.
