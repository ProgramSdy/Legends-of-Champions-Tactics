## A. Generic Battle API Findings

`POST /api/v1/battles` is **registered in Public today**, because `battle_api/app.py:492-526` declares it unconditionally; the only mode-gated creation router is `/api/v1/debug/battles` (`battle_api/app.py:88-89`; `battle_api/release_mode.py:17-32`). The fact that a normal screen does not call the generic route does not make direct HTTP requests return 404. Its optional seed and unlocked-team check are separate issues (`battle_api/models.py:346-376`; `battle_api/app.py:500-526`).

The generic handler calls `registry.create` without stage, Arena, or progression-profile launch context (`battle_api/app.py:500-526`; `battle_api/adapter.py:4109-4144`). Its session cannot use structured completion: `/api/v1/battles/{id}/completion` rejects a non-stage session as `battleNotStageScoped` (`battle_api/app.py:725-732`). This does not make the directly reachable generic route harmless; it can still allocate and operate RAM battles.

**Verdict:** No currently enabled normal Public feature needs the generic creation route. It is safe *for current Public gameplay* to conditionally **unregister** it using the existing fail-closed server release-mode boundary, so direct Public HTTP returns 404 while Development retains it. This is a recommendation for a later approved implementation, not a change made here. Before doing so, check API clients outside this repository and the owner’s intended status of future free-form play; adjust mode-specific API/OpenAPI tests without silently removing the Development seam. Shared `GET/commands/preview/completion` battle routes must remain for Stage/Arena and gain ownership checks; generic creation restriction does not secure those routes by itself.

## B. Resign and Battle Lifecycle Findings

**Resign is offered, not required.** `BattleScreen` shows a `RESIGN` button when `onResign` exists, opens a Yes/No modal, and invokes the passed callback only on Yes (`web-ui/components/battle/BattleScreen.tsx:815,853-863`; `web-ui/tests/battle-screen.test.tsx:154-169`). In a structured battle, that callback is `closeLiveBattle`, which sets React `activeLaunch` and background to `null` (`BattleExperience.tsx:211-214,416-425`). Arena sets `activeBattle` to `null` (`ArenaRunExperience.tsx:218-232`); Debug clears its configuration (`DebugBattleExperience.tsx:78-91`). None calls a battle-resign/abandon endpoint. Arena's separate **Give Up Current Run** deletes the persisted Arena run, not the live battle session (`ArenaRunExperience.tsx:200-213`; `battle_api/app.py:330-348`).

**Server result:** Yes on Resign only unmounts the provider/presentation. It does **not** mark defeat, abandonment or another authoritative terminal outcome, and it does not delete/invalidate the RAM session. No battle resign route or registry remove/expiry method exists (`battle_api/app.py:621-766`; `battle_api/adapter.py:4099-4149`). An unfinished session still fails a completion request because completion requires an authoritative ended friendly victory (`battle_api/app.py:446-464,734-752`). However, a previously won but uncommitted session may still commit via a direct request after UI Resign, and a party retaining its battle ID can still issue state/command/preview calls because those routes only look up the ID (`app.py:621-700`). Thus “will not count as a victory” in the modal is a UI expectation, not a backend abandonment guarantee.

| Scenario | Current observed/code-backed behavior | Guarantee absent |
| --- | --- | --- |
| Browser refresh, Back, tab close, direct navigation | Provider/snapshot live in component/class memory; no unload/pagehide battle termination is wired in the battle components. A fresh route mount can create a new battle, while old RAM session remains in the server registry (`BattleExperience.tsx:125-214`; `liveProvider.ts:850-890`; `adapter.py:4099-4149`). | No immediate server abandonment; browser close cannot be detected reliably. |
| Save-slot switch in another tab/caller | Global active-slot selection changes (`battle_api/progression.py:614-625,768-795`). Stage/Arena launch binds a profile and completion later requires it still be globally active (`battle_api/app.py:359-405,538-619`; `progression.py:1356-1365,1481-1487`). | This prevents some wrong-slot reward writes, but does not terminate the old battle or prove caller ownership. |
| New Stage/Arena battle after leaving an old one | A new attempt ID launches a distinct session; `BattleRegistry.create` inserts it in `_sessions` without checking another active battle (`battle_api/adapter.py:4099-4149`; `battle_api/attempts.py:34-80`). | No one-battle-per-profile/player rule or global capacity bound. |
| Completion/retry | UI calls completion only after ended outcome, and store uses `BEGIN IMMEDIATE` plus completion receipts/duplicate handling (`BattleExperience.tsx:233-275`; `ArenaRunExperience.tsx:187-198`; `battle_api/app.py:427-468,712-766`; `progression.py:1346-1413,1467-1614`). | No authenticated owner, server-side abandonment state, revocation or expiry check. |

**Current concurrency/expiry:** Registries are process-local maps; `BattleAttemptRegistry` locks one attempt key and caches the original envelope, but neither registry has normal removal, active-count cap, inactivity timestamps, TTL or warning data (`battle_api/attempts.py:34-80`; `battle_api/adapter.py:459-479,4099-4149`). Session locks serialize commands on one battle and transactional receipts make duplicate wins idempotent; they do not serialize Resign against a new launch, prevent multiple live battles, or guarantee no old completion after a client leaves.

**Races:** UI Resign versus in-flight command/completion can leave server work running after the screen disappears. Two new attempt IDs can create two sessions. Slot switch/overwrite after launch may block completion or invalidate the old profile but does not remove the session. Arena abandon/replacement can leave an obsolete RAM battle. Existing attempt fingerprint checks, session locks, authoritative victory checks and SQLite receipts are reusable (`attempts.py:41-75`; `adapter.py:1354-1384`; `app.py:446-464,734-752`; `progression.py:1346-1413,1467-1614`), but none is a substitute for player ownership and atomic abandonment/expiry enforcement.

For two separately launched Stage battles, distinct battle IDs can yield separate completion receipts even where unique reward records prevent a second identical reward grant; there is no one-active-battle rule (`battle_api/progression.py:1488-1614`). For two Arena sessions on one node, the first committed victory advances it and the later one fails the current-node/order check (`progression.py:1363-1380`). A further policy gap lies between an authoritative terminal victory and its separate HTTP reward-commit request: expiry or Resign in that window could either discard an uncommitted win or allow a later commit unless the implementation defines one ordering and settlement rule.

## C. Task B Implementation Impact

These are **approved future targets**, not current behavior:

| Target | Current classification | Minimal future impact / precise boundary |
| --- | --- | --- |
| At most one active battle per Player ID | **Missing** | Once Player ID exists, atomically reserve a player battle lease before session creation; release on authoritative finish, resign, expiry or safe failed creation. Define whether an ended-unacknowledged battle still occupies the lease. |
| Global configurable cap 20 active battles | **Missing** | Reserve/release under one server-side capacity authority, not a UI count; test concurrent starts and rollback. A process-local cap only works with the approved single-worker architecture. |
| 30-minute inactivity expiry | **Missing** | Add server-owned last-accepted-action/expiry time, checked under session/lease lock on every operation and cleaned in bounded fashion. Avoid client-only timers. No-resume/abandonment must suppress later completion/reward. |
| 5-minute and 1-minute warnings | **Missing** | Publish authoritative expiry/deadline or warning state in a narrow typed response/event; UI timer can display it but server decides expiry. Warn once across rerenders and account for clock skew; do not reset server time on polling. |
| Only successful server-accepted battle action resets timer | **Partially supported action boundary; timer missing** | `BattleAdapter.submit` validates, then `_resolve` returns `accepted: true` and increments revision; rejected commands do not resolve (`battle_api/adapter.py:1354-1384,2895-3034`). Cached duplicate command IDs can return a prior accepted result without a new action. Future timer should reset only on a newly accepted command, not on `GET /battles`, preview, rejected/duplicate retry, UI skill selection, playback, or automatic turns unless owner explicitly decides otherwise (`adapter.py:1354-1393`; `app.py:621-700`). |
| No Battle Resume; unfinished/abandoned gives no rewards; committed rewards remain | **Partially supported** | No live reload recovery exists and friendly-victory guard/receipts protect unfinished/double award. But old RAM sessions survive UI departure; add server terminal abandonment and check it in command/preview/completion. Never roll back a receipt already committed before later resign/expiry. |
| Preserve Resign UX | **UI supported; server semantics missing** | Keep existing Yes/No modal, but Yes must call an authenticated idempotent server resign endpoint and await its terminal acknowledgment before leaving, with safe error/timeout handling. No combat-rule rewrite is needed. |

**Timer ambiguity for owner/design:** An accepted player `useSkill` may synchronously drain multiple automatic turns and round effects inside one request (`battle_api/adapter.py:1354-1384,2895-3034,3290-3365`); client event playback may take additional time. Clarify whether the 30-minute clock is measured from server acceptance/start or completion of the full request, and what happens if expiry is reached while a command is executing or while the player watches animations. Preview, state polling, duplicate retries and AI-only automatic turns must not silently count as a successful player action. This audit does not choose policy. Future regression gates should cover parallel player/global cap allocation, release on every terminal path, 30/5/1 clock boundaries with a fake clock, duplicate/rejected/preview non-reset, playback-warning behavior, Resign-vs-completion ordering, slot/session revocation, and already-committed reward preservation.

## D. Final Recommendation

1. **Generic route:** Current Public navigation does not need `POST /api/v1/battles`; conditionally unregister it in Public after the owner confirms no external Public client or intended free-form mode relies on it. Development/test use remains, and Stage/Arena keep their distinct creation endpoints. Do not confuse this route removal with authentication of shared battle routes.
2. **Battle lifetime:** Current Resign is frontend-only and can be bypassed by navigation. Implement future server-owned resign/abandonment, one-per-player and global-cap leases, expiry, and completion gating as a coordinated ownership change. Retain the existing modal and transactional/idempotent reward machinery, but do not call the present behavior a defeat or guaranteed abandonment.
3. **Owner decisions before implementation:** Confirm generic free-form Public policy; decide whether an ended but unacknowledged battle holds a lease and how a victory reached just before expiry/Resign may be settled; define expiry timing during in-flight resolution/playback and whether successful automatic/forced turns count as activity; decide UX for failed Resign acknowledgment and the warning source contract. Browser close cannot guarantee prompt server notification, so TTL/cleanup is essential. External client inventory and an isolated runtime concurrency test would reduce remaining uncertainty; neither was available/performed in this source-only audit.
