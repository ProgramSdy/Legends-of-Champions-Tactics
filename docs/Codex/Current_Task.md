# Current Task

**Status:** Completed

**Task:** UI-028 — Hero Gallery Skill Reference Metadata and Editable Expanded Cards

**Owner request date:** 2026-10-10

## Objective

Enhance the expanded skill cards in the existing Hero Gallery with authoritative
skill reference facts and human-editable introductions, without changing
Gallery layout/accordion interaction, battle rules, or frontend authority.

Each expanded card must show only relevant facts in a compact responsive
two-column grid:

- editable skill introduction;
- Base Damage or Base Healing where an audited result is available;
- Target Type;
- Skill Type;
- Attack Type;
- Damage Nature; and
- Damage Type.

The first implementation/audit pilot is Priest Comprehensiveness's three skills
and Paladin Protection's Hammer of Revenge. After the pilot gate succeeds,
apply the same audited structure to every skill in the approved ten-hero web
roster. Numeric values appear only where an audit establishes them safely.

## Background

UI-027 added the Hero Gallery through the read-only `GET /api/v1/heroes`
catalogue. It currently supplies stable hero identity, configured starting-stat
and resistance ranges, an active/passive skill inventory, and unlock source;
it deliberately does not construct heroes or consume RNG.

The existing Gallery stores editorial introduction/battle-style/skill copy in
`web-ui/lib/manual/heroManualContent.ts`. This task moves that editable copy to
validated YAML under `web-ui/content/hero-gallery/`, while keeping gameplay
metadata and numeric reference values authoritative in Python. React must not
parse Python source, reconstruct combat rules, or derive target semantics from
raw `target_type="single"` metadata.

Base Damage/Base Healing is a **reference value**, not Battle Information
Transparency and not a promise of actual received damage/HP restoration. It
describes audited baseline skill power across configured caster starting-stat
ranges before target-specific receipt/mitigation, subject to each skill's
documented conditions. It must never be generated by random sampling or by
creating randomized heroes.

## Requirements

### Expanded card presentation

- Preserve existing Gallery route, concept layout, selected-hero behavior,
  tabs, accordions, assets/fallbacks, ownership, navigation, input/audio, and
  responsive behavior.
- On expansion, render a compact, readable facts grid that uses two columns
  where space permits and one column at narrow widths. It must not become a
  battle-preview panel or a dense technical dump.
- Translate stored internal values to player-friendly labels, for example
  `ranged_instant` to **Ranged Instant**. Do not expose raw enum formatting.
- Show only fields relevant to the skill. Healing shows **Base Healing**;
  ordinary damage shows **Base Damage**; hybrid actions show separate audited
  Damage and Healing entries; buffs, passives, protection, and non-damaging
  actions must not acquire invented damage classifications.
- A missing relevant classification is **Unclassified** only when authoritative
  data says the damage concept applies but does not classify it. **Not
  applicable** means the field genuinely does not apply. Never silently turn
  `NA`/missing data into an assumed default.
- For an unavailable numeric result, show concise truthful wording explaining
  why it cannot currently be established, rather than a guessed value.

### Authoritative catalogue metadata

- Extend `GET /api/v1/heroes` additively with typed reference metadata keyed
  by stable hero `definitionId` and stable `skillId`. Preserve current clients
  and the frozen v1 envelope/roster compatibility.
- Metadata must cover audited player-facing target semantics, skill type,
  active/passive status, attack type, damage nature, damage type, and a typed
  Base Damage/Base Healing reference result or explicit unavailable/inapplicable
  reason. Include target quantity only where it helps describe target type.
- Derive target labels from the adapter's audited legal target semantics. Raw
  `target_type="single"` alone is insufficient: distinguish self, one ally,
  one enemy, ally-or-enemy hybrid, and multi-target behaviour accurately.
- Obtain mechanics classifications from authoritative Python definitions and
  audited adapter/engine paths. Do not parse Python source files at runtime or
  duplicate combat logic in React.
- Catalogue reads remain static, deterministic, read-only, and RNG-free: no
  randomized hero construction, skill execution, battle session, status update,
  progression mutation, or client-provided metadata.

### Editable YAML presentation content

- Move current hero introductions, battle-style summaries, skill introductions,
  and optional labelled strategy tips to human-editable YAML files under
  `web-ui/content/hero-gallery/`. Use stable definition IDs and skill IDs,
  multiline text support, and preserve the existing wording during migration.
- Define and validate a strict content schema: every approved hero/skill needs
  its required editorial entry; unknown/stale IDs, duplicate entries, missing
  required copy, malformed YAML, and inappropriate mechanical numeric fields
  must fail validation with an actionable error.
- Keep editorial YAML separate from authoritative mechanical metadata and
  numeric values. Future metadata refreshes must never overwrite manually
  edited YAML.
- Add a short `web-ui/content/hero-gallery/README.md` explaining exactly where
  descriptions/tips are edited, stable-ID rules, YAML validation, and whether
  the local dev server/build must be restarted or rebuilt for edits to appear.
- Use a safe, deterministic build/runtime loading approach compatible with the
  existing Next/Vinext environment. Do not add an unvalidated string parser or
  make browser fetches the authority for local editorial files.

### Base Damage and Base Healing reference rules

- Treat these as baseline skill power across the hero's configured starting
  stat ranges **before target Defence, target resistance, shields, immunity,
  evasion, formation, HP cap, or receipt modifiers**, unless a skill's audited
  formula genuinely makes one of those an inseparable baseline input. Do not
  label the result as actual damage dealt or HP restored.
- Every numeric range needs an audited proof of valid bounds, including
  correlated input stats, conditionals, rounding/floor/ceil, ordered targets,
  and random variation. Do not assume minimum/maximum inputs automatically
  create valid bounds and do not estimate by random sampling.
- Prefer small shared pure calculation functions/constants when they can safely
  be shared between execution and reference evaluation. Preserve current live
  formula, rounding, RNG calls/order, status lifecycle, event ordering, and
  gameplay behavior. Never replace a legacy callback wholesale merely to make a
  Gallery number convenient.
- Display explanatory copy appropriate to the audited skill, such as “Before
  target Defence. Actual damage varies with the caster's Damage and the
  target's Defence.” Do not use the example wording where its premise is false.
- Handle each special case explicitly: conditional bonuses separate baseline
  power from conditions; periodic damage distinguishes immediate and per-
  activation facts and shows totals only with verified lifecycle assumptions;
  multi-target skills retain per-target/ordered-target differences; healing
  distinguishes power from actual restored HP; hybrids have separate entries;
  buffs/passives/protection describe effects without fabricated damage.
