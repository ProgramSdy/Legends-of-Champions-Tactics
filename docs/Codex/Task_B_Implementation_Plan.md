# RELEASE-002-PLAN / Task B — Implementation Plan

**Date:** 2026-11-11 (Australia/Sydney). **Status:** Planning only; owner approval required before any phase. **Scope:** one repository, current combat engine/mechanics, five player-facing slots, one FastAPI worker, SQLite, and RELEASE-001's fail-closed Development/Public split. The owner brief at the task attachment is authoritative; this document does not authorize code, schema, save, build, or deployment changes.

## A. Executive Summary

Public multiplayer use is blocked by unauthenticated global saves and battle-ID-only access, not by a need to replace SQLite or the engine. Implement Task B in **nine gated phases**: (1) schema/identity, (2) sessions/recovery/abuse, (3) owned saves, (4) battle ownership/capacity, (5) Resign/expiry, (6) durable Victory settlement, (7) Public seeds/diagnostics, (8) frontend integration, (9) backup/release validation. Phases 1–8 must be deployed as one closed Public security boundary; intermediate work may ship only to isolated Development/test. Phase 9 is a mandatory pre-Public gate. Do not expose player-facing Public writes while identity, ownership, and settlement are only partly installed.

The principal design is: a server-generated Player ID with one revocable cookie session; player-keyed slots/active selection; SQLite-backed battle reservations atomically limited to one per Player ID and 20 globally on the approved single worker, with RAM engine sessions; an immutable battle owner/launch slot; an authoritative 30-minute inactivity deadline; and a terminal-Victory path that **commits outcome and existing idempotent reward effects in SQLite before returning a confirmed Victory**. A later UI completion call becomes an idempotent receipt read, not the sole settlement trigger. Resign/expiry cannot erase already committed victory. Failure before durable confirmation remains a retryable pending state and must never be presented as confirmed. That acknowledgment boundary is essential for disconnect safety without implementing live battle resume or full replay.

## C. Approved Product Requirements and Constraints

The implementation must use 3–20 ASCII `[A-Za-z0-9_]` Player Names, preserve case, permit duplicates, and forbid Pre-Alpha rename. Names are display-only; server-generated Player IDs own five independent slots. Recovery is a securely generated 16-character uppercase unambiguous base-32 code (80 bits), formatted `XXXX-XXXX-XXXX-XXXX`, displayed only at issue with Copy and explicit saved-code confirmation; it does not expire and has no ordinary regeneration. An authenticated **Forgot Recovery Code** action replaces it immediately; without both session and code, there is no self-service recovery. Recovery never depends on Player Name.

One active device session per Player ID, 30-day sliding expiry, secure rotation, logout and recovery revocation are mandatory. Use HTTPS, same-origin frontend/API, `Secure; HttpOnly; SameSite=Lax` cookie, Origin/CSRF checks, no browser-stored auth secrets, and at most 10 failed recovery attempts per IP in 15 minutes followed by a 15-minute temporary block; no permanent account lock. Proxy trust, privacy-safe logs and global abuse controls are part of the boundary.

Public uses a clean separate SQLite DB outside replaceable artifacts; Development saves remain untouched and are **not** imported. Back up daily and pre-release, retain seven daily backups plus explicit release backups, keep off-VM copies, and test restoration. One active battle per Player ID and configurable initial global cap 20 are server-atomic on one worker. No resume. The server expires unfinished battles after 30 minutes of inactivity; only a *newly accepted player action after complete server-side resolution* resets the timer. Polling, preview, rejected/duplicate commands, UI selection, automatic turns and playback do not. Do not interrupt an in-flight valid command. Show one-time five- and one-minute warnings from server timing.

Resign keeps Yes/No, but Yes must await an authenticated idempotent server acknowledgment; failed/timeout requests remain in the Battle UI with retry. Resign/expiry before Victory means no reward; once server confirms terminal Victory, reward must settle exactly once despite browser loss. Public rejects caller seeds, records effective server seed and minimal diagnostic metadata indefinitely for Pre-Alpha, without secrets or event replay. Public does **not register** generic `POST /api/v1/battles` (direct 404); Development retains it separately from Debug. Shared Stage/Arena battle routes remain and become owner-protected. These are fixed owner requirements, not open alternatives.

## D. Proposed Technical Architecture

**Identity/session:** Keep FastAPI as authority. Generate a UUID Player ID and `secrets`-based code/token. Use the proposed alphabet `23456789ABCDEFGHJKLMNPQRSTUVWXYZ` (exactly 32 symbols; no `0`, `1`, `I` or `O`) with 16 independent `secrets.choice` draws, formatted four-by-four. Normalize Recovery Code only by stripping display separators and uppercasing, then verify exact 16 symbols. Recommend an indexed keyed HMAC-SHA-256 verifier over a domain-separated code value, with a server-held key outside SQLite, constant-time comparison, and key version for rotation. An 80-bit random code does not need a user-password KDF for dictionary resistance; the secret HMAC key protects a copied database. Never store/log plaintext or place code in a URL. Issue the code only in a no-store enrollment/replacement response, and persist a `recovery_confirmed_at` flag after an explicit saved-code acknowledgment; an unconfirmed new session can access only onboarding/acknowledgment, not slots. Rotate the session credential at recovery and on a bounded renewal schedule, with atomic token-hash replacement and a short, explicitly tested same-session race policy; recovery increments a per-player session generation and invalidates the former device immediately. Use a 256-bit opaque session token in a host-only `__Host-` cookie with the owner-required flags and no `Domain`; store only a token verifier and expiry. A server-side CSRF secret/token bound to the session, conveyed in a non-cookie response/header to same-origin JavaScript, plus exact Origin/Fetch-Metadata checks gates state-changing requests. `SameSite=Lax` is defense in depth, not the only CSRF control ([OWASP session guidance](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet), [OWASP CSRF guidance](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)).

**Persistence:** Add Player ownership to slots/profiles and replace global active-slot selection with a player-keyed record. Retain profile-keyed unlock/progression/reward/Arena tables where possible, but every Public service method receives authenticated Player ID and verifies the profile belongs to that player *inside its transaction*. Do not accept client Player/profile IDs as authority. Public starts with a new clean v5+ DB; existing anonymous Development v4 data remains in an isolated legacy-Development compatibility path without invented identities or recovery credentials. Never copy it to Public.

**Battles:** Extend the existing registry/attempt boundary rather than forking engine mechanics. Generate the battle ID before launch, then under the one-worker per-player lifecycle lock use one short SQLite `BEGIN IMMEDIATE` transaction to expire stale leases, reject an existing lease for this player, count all active and provisional leases, and insert a provisional lease only when the count is below the configured 20; commit before RAM construction. Give provisional construction a configurable initial **two-minute TTL**, distinct from the 30-minute active-battle inactivity deadline. Pass that same ID into an adapted `BattleRegistry.create`, then conditionally activate the still-valid lease in a second transaction. If RAM construction or durable activation fails—including a provisional TTL expiry—compensate by removing the RAM session/attempt binding and releasing the provisional lease; expose neither state nor capacity until activation succeeds. The SQLite transaction, not a RAM count, is the capacity authority. RAM remains the engine-session store, while a durable lease/diagnostic row tracks the active reservation and is reconciled on process startup (old RAM battles cannot resume). Bind `player_id`, launch `slot_id`, `profile_id`, session generation, route context, creation time, `last_accepted_action_at` and `expires_at` to the battle. All state, command, preview, Resign and settlement calls authenticate and check this owner/binding; battle ID is only a lookup key. Keep terminal records/receipts for idempotent reads but remove them from active capacity. Bounded lazy cleanup on requests plus an optional lightweight periodic sweep within the same worker can expire inactive RAM entries without a new worker or broker; correctness checks occur synchronously on each protected operation, not only in the sweep. Browser unload is best-effort and never authoritative.

**Terminal settlement:** For Stage/Arena, after engine resolution reaches friendly Victory and while the battle is exclusively locked, execute a single SQLite `BEGIN IMMEDIATE` operation that records the terminal outcome, applies the existing stage/Arena receipt/progression/reward change exactly once, stores the original reward/result payload, and releases the active lease before returning the accepted terminal response. Refactor current `commit_victory`/`commit_arena_victory` into transaction-scoped helpers that share one connection; do not nest their current separate `BEGIN IMMEDIATE` calls (`battle_api/progression.py:1346-1413,1467-1614`). The diagnostic/settlement record is the durable confirmation point. A lost response is safe: command-ID replay and completion GET/POST return the durable receipt *and original notification data*; current duplicate Stage completion returns an empty reward list, so it cannot alone reconstruct a lost first notification (`progression.py:1488-1505`). If SQLite cannot commit, do **not** acknowledge a confirmed Victory, release the lease, or allow Resign/expiry to erase pending resolution; retain a retryable terminal-pending state in RAM and retry settlement server-side on the next bounded sweep/request. A process failure before that durable commit cannot be called a confirmed Victory; tests must prove no successful terminal response was emitted. This avoids a browser-dependent later completion call, while retaining it as idempotent acknowledgment. Defeat/draw settle authoritative outcome without rewards. The strict crash-with-DB-unavailable window and pending-state retry semantics are called out in Section J for explicit acceptance testing.

**Public seeds/diagnostics:** Public Stage/Arena creation rejects any supplied seed and draws `secrets.randbits(256)` before adapter construction; the actual effective seed is held server-side, not echoed. Generic creation is absent in Public. Development generic/Stage/Debug retain explicit seeds for deterministic tests. Store 256-bit seed as fixed-length binary or canonical hex text, not SQLite signed INTEGER. One minimal diagnostic row per battle contains IDs, launch slot/profile, effective seed, build version, start time, type/stage/run/node context, authoritative outcome and settlement/lifecycle timestamps/status; no code/token/IP/full event log. Retention is indefinite for this Pre-Alpha as approved. Arena's persisted legacy node `battleSeed` is not the fresh combat seed (`battle_api/app.py:365-405`; `progression.py:1137-1171`).

## G. Security and Concurrency Design

**Lock/transaction order:** In the approved single FastAPI worker, use a keyed per-player lifecycle lock for recovery, protected battle operations and launch/Resign coordination. Acquire that before a session lock when both are needed. SQLite `BEGIN IMMEDIATE` is the **only authority for global-capacity counting and durable lease insertion/release**: in one transaction, expire eligible stale rows, check this player's lease, count active plus provisional rows, and insert provisional lease only if below cap. A registry-global RAM lock may protect dictionary mutation but must never act as a separate capacity counter. Do not hold SQLite transactions across engine resolution; avoid calling back into a player lock while holding a DB transaction. Code review and adversarial concurrency tests must establish this exact order; async FastAPI routes currently delegate synchronous store work to threads (`battle_api/app.py:144-165`), so do not block the event loop with SQLite or a long engine operation.

**Race winner rules:** Recovery/revocation obtains the player lock; a command already fully accepted/settled before revocation remains valid, while one that acquires the lock after revocation fails. As part of that same ordered lifecycle change, revoke/abandon the old session's *unfinished* battle and release its lease, so the recovered device is not blocked for 30 minutes; an already durable Victory/reward is untouched. Command, Resign and expiry serialize at the battle/session lock. A newly accepted command that starts before expiry resolves fully, then updates deadline *after* resolution; if it produces Victory, settlement happens before its response and wins over later Resign/expiry. If Resign or expiry commits first, later command/settlement is rejected. Duplicate command ID returns its original result but is not a new activity event (`battle_api/adapter.py:1354-1381`). Save-slot overwrite must invalidate or reject battles bound to the old profile without redirecting rewards. A terminal confirmed Victory releases capacity even if the browser never acknowledges it; already committed rewards survive later logout, Resign, expiry or browser close. A pending uncommitted terminal result must not be misreported as confirmed and must not be silently discarded by cleanup.

**Abuse and trust:** Public deployment **must demonstrate** sole approved ingress (Nginx for the private API) and private FastAPI binding before release; the current GCE network/TLS/proxy topology has not been inspected or verified. Trust `X-Forwarded-For` only from the configured proxy IP and take the documented canonical client address; direct or spoofed headers must not evade limits. Record failed recovery attempts in SQLite under an HMAC-derived IP key; the 10th failed attempt within a rolling 15 minutes sets a 15-minute block, and subsequent attempts are denied until its boundary. Return uniform messages/timing where practical, avoid account enumeration and raw IP/code/session logging, limit body size and overall request rate at proxy as availability controls. Preserve the owner-approved per-IP rule without adding permanent account lock. CSRF validates Origin plus a session-bound synchronizer token for unsafe methods; GET remains side-effect free. Configure cookie rotation atomically and test concurrent tabs and recovery invalidation.

## I. Deployment, Backup, and Rollback Plan

Public frontend and `/api/v1` must have **one browser-visible HTTPS origin**. The current vinext Worker has no API proxy (`web-ui/worker/index.ts:28-44`), so Phase 9 must first verify the intended frontend host: either Nginx fronts both a frontend runtime and the privately bound one-worker Uvicorn API on GCE, or the Worker proxies same-origin `/api/v1` to a protected GCE Nginx origin using server-only configuration. Do not expose backend CORS as a substitute; test cookie, `Set-Cookie`, Origin, CSRF, timeout and trusted-client-IP forwarding end to end for the chosen route. Keep `LOCT_RELEASE_MODE=public`, Public artifact guard, and Development-only debug/generic paths; separate `BATTLE_API_PROGRESSION_DB` path on a durable mounted volume outside checkout/artifact. Startup should refuse a missing/unwritable Public DB path or required secret instead of silently creating an empty replacement. Secrets (HMAC key, cookie/signing/CSRF material, backup credentials) come from protected server configuration, not `NEXT_PUBLIC_*`, SQLite, source or logs. GCE e2-micro sizing is an empirical release gate, not assumed capacity.

Use SQLite's consistent online backup API or controlled quiesced backup, not an uncoordinated copy of a live `.sqlite3` (especially if WAL is enabled); verify `PRAGMA quick_check`, schema version, FK integrity and a checksum on an isolated copy ([SQLite online backup](https://sqlite.org/backup.html), [WAL behavior](https://www.sqlite.org/wal.html)). Schedule daily backup and keep seven latest daily snapshots; make a separate labeled backup before each release and retain it under an explicit manual release-backup policy. Transfer encrypted/protected copies off-VM (for example GCS), restrict access, monitor failures/space, and never package DB/WAL/SHM in frontend/backend release artifacts. No automatic diagnostic purge during Pre-Alpha.

Restore drill: quiesce writes, preserve the current volume, download/decrypt a selected backup into an isolated path, validate integrity/schema/player-slot/receipt counts without exposing private rows, start a staging process against that copy, run a safe read-only smoke, then document atomic path swap and rollback order. A real restore requires owner-authorized outage and must never be performed by an automated test against live saves. Migration is rehearsed on a copy, with backward-incompatible schema rollback via verified backup rather than ad-hoc reverse SQL. Keep old artifact and DB backup separately; rolling back code alone against a newer schema may be unsafe. Before Public enablement run an isolated 20-battle e2-micro stress: representative 1v1/2v2/3v3 with 3v3 worst-case memory, simultaneous launches/commands/previews, 21st rejection, failed-factory rollback, expiry cleanup, SQLite busy and disk-pressure tests. Record observed headroom/latency and set alert thresholds from measurements rather than inventing them.

## J. Risks, Assumptions, and Remaining Technical Questions

| Risk/unknown | Consequence and required verification |
| --- | --- |
| Partial Public activation | Authenticated users could still share global slots, or owned saves could be reached anonymously. Keep Public write/launch gate closed until phases 1–3 and 4–6 activate together. |
| Victory durability gap | A terminal engine outcome acknowledged before SQLite commit can be lost after browser/process failure. Design and test acknowledgment-after-durable-settlement; define retry of RAM terminal-pending state. A simultaneous DB outage and process crash before durable commit cannot be repaired without durable action/checkpoint logging, which would enlarge scope; never claim such an uncommitted internal outcome was confirmed. |
| Lock order / capacity leak | Per-player/session/DB inversion or failed RAM creation/durable activation can deadlock, create an orphan RAM battle, or strand one of 20 leases. Count/insert solely inside SQLite `BEGIN IMMEDIATE`, pre-generate the battle ID, compensate both stores, and prove failure/race cases. |
| Session rotation vs multiple tabs | A strict token swap can fail concurrent tabs; an old-token grace can create exposure. Select a bounded rotation cadence and same-session race policy, then test revocation precedence. No second *device* session may survive recovery. |
| SQLite/VM operations | Busy writes, disk full, wrong mount, backup inconsistency or restore failure can lose progress. Rehearse and measure on isolated e2-micro; choose thresholds/RTO after evidence. One worker is fixed; multiple workers need a later redesign. |
| Recovery lookup/key custody | Lost HMAC key makes stored verifiers unusable; compromised key weakens DB protection. Approve exact 32-character alphabet constant, protected key rotation/backup runbook, and recovery-verifier migration strategy. |
| Proxy/rate-limit trust | Wrong Worker→Nginx or browser→Nginx forwarded-IP chain can let attackers evade the 10/15 rule or block innocent users behind NAT. Verify the selected topology, canonical IP extraction and global abuse limits; do not trust arbitrary request headers. |
| Version/contract compatibility | Current `1.0` envelope and separate completion call are widely tested. Plan additive fields/endpoint versioning, Dev test migration, and direct Public 404/OpenAPI checks before flipping the mode gate. |

The fixed owner policies are not open: duplicate names, 80-bit formatted code, no ordinary regeneration, one device, 30-day sliding session, 30-minute battle inactivity, 5/1 warnings, cap 20 initially, clean Public DB, indefinite diagnostics, Public generic route absence, and no Battle Resume. Remaining *technical* choices are secret storage/rotation/runbook; same-session token rotation overlap; actual same-origin Worker/Nginx routing and trusted-client-IP configuration; build-version source and minimal diagnostic context serialization; response/error naming; quantitative e2-micro headroom and backup restore objective after measurement. If the owner interprets “server determines Victory” as including an uncommitted engine calculation during simultaneous DB outage/process crash, that guarantee would require a durable pre-resolution journal/checkpoint and explicit scope approval; this plan instead treats **server-confirmed** Victory as the durable transaction boundary in the approved brief.
