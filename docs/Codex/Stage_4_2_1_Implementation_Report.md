## Tool and actual Public workflow

`tests/tools/public_battle_load.py` is a standard-library Python CLI. Its default invocation prints a plan and sends **zero HTTP requests**. An executed run requires `--execute`, an HTTPS origin, and explicit positive duration, request-count and global request-per-second budgets. A non-loopback target additionally requires `--allow-production` and the fixed `--owner-authorization` acknowledgement. These flags are safety interlocks, **not Owner permission**. Redirects are not followed; a redirect, 429, capacity rejection or timeout stops the shared run. Ambient HTTP proxy settings are disabled, so a loopback target cannot be rerouted through them. Optional `--ca-file` trusts an isolated local certificate; the unsafe-TLS option is limited to loopback and was not needed for the successful local run. `--players` (alias `--concurrency`) supports 1–100 independently authenticated workers; no ramp occurs automatically.

Each worker creates a uniquely named **new disposable** Public player, discards the one-time Recovery Code, acknowledges it, creates its own slot 1, and checks the authoritative Stage listing. Fresh profiles cannot directly enter a 3v3: the tool legally wins Warrior's Barrack Learner stages 1 (2v2) and 2 (1v1), then plays stage 3 (3v3). It uses a separate cookie jar and CSRF token per worker, exact Origin, unique attempt and command IDs, current revision, and only the snapshot's published `legalActions`/`validTargetIds`/target cardinality. It does not supply a Public seed, infer or change combat rules, access Development generic battles, replay a timed-out command with a new ID, or fabricate a terminal outcome. The server's settled receipt distinguishes a real friendly victory from a defeat/draw. Attempts, commands, total requests and elapsed time are bounded. A failed preflight or 3v3 within the bound is reported rather than bypassed. If a bound interrupts a live battle, no extra cleanup request is forced beyond that bound; the server's normal inactivity expiry releases its lease.

Terminal output reports request counts, average and nearest-rank P95 latency, throughput, error/timeout rates, category counts (`api_error`, `rate_limit`, `battle_rule`, `capacity`, `timeout`, `redirect`, `tool_error`), attempted/settled/unfinished battles, and 3v3 settlements/friendly victories/nonvictories. Optional CSV uses an exclusive-create path and contains only worker index, endpoint **label**, latency, HTTP status and category. It excludes response bodies, cookies, CSRF and Recovery Codes, account/profile IDs and battle IDs. Published battle-rule codes are classified separately from API failures; a 2xx `accepted: false` command is also a battle-rule rejection.

## 2026-11-22 follow-up — reusable dedicated test-player pool

The CLI now has explicit `--mode create`, `--mode reuse`, and `--mode reconcile` paths. Executed runs require `--pool-file` at an absolute path outside Git, in an existing owner-private `0700` directory. The pool and its stable lock file are owner-owned `0600`; an exclusive process lock prevents concurrent runs using that same pool file. The JSON manifest binds one exact origin to unique Player/Profile IDs and Recovery Codes. Pool writes use an exclusive `0600` temporary file, flush/fsync and atomic replacement. Codes are never printed, written to CSV, or accepted through a command-line argument. A pre-enrollment reservation is persisted before `POST /players`: if a response is lost before the one-time code is saved, the uncertain reservation blocks automatic replacement and requires manual operator investigation.

Create mode first resumes any clean `provisioning` accounts; it will not silently replace one whose recovery fails. It then adds only the accounts needed to reach `--pool-size` (default: `--concurrency`). `--pool-size` and `--concurrency` are separate so a pool can grow through **2 → 10 → 30 → 50 → 100** with small concurrent batches and the existing global request/rate/duration ceilings. A bounded run may stop partway through expansion; rerunning create first resumes the recorded identities, then adds the remaining number. Newly enrolled accounts have their Recovery Codes persisted immediately, are acknowledged, own slot 1, and legally complete the Warrior's Barrack prerequisite stages before the 3v3 attempt.

Reuse mode selects distinct `ready` accounts from the pool; it never enrolls or creates/overwrites a slot. Each worker uses the backend recovery endpoint, confirms the returned Player ID, checks the owned slot/profile and loads it, checks authoritative stage-3 access, then uses fresh battle attempt and command IDs. A completed prior battle ID is probed for the server's `battleNoLongerActive` result before launch. The pool marks a battle `in_flight` **before** its launch request and returns to `ready` only after an authoritative settlement; interrupted/uncertain states block reuse. The backend's one-active-battle-per-player lease check remains authoritative. Recovery itself revokes the old session and invalidates its unfinished battles, so the pool must not be copied or operated concurrently from another host; the local file lock alone cannot enforce cross-host exclusivity or observe an unrelated battle started outside this tool.

An interrupted account requires a separate explicit `--mode reconcile --confirm-reconcile ABANDON_INTERRUPTED_TEST_BATTLES` operation. This intentionally uses recovery to revoke the old session/abandon any unfinished test battle, verifies the owned slot and prior known battle's non-active result, and marks the account `ready` only if stage 3 is unlocked. Otherwise it remains `provisioning` for a later create-mode continuation. If recovery fails or an enrollment has no saved code, the account stays blocked; no replacement is created or production row deleted. Operators must inspect such ambiguous records and decide separately. A local/direct-Uvicorn recovery fixture must not mark its own peer IP as a trusted proxy without an overwritten `X-Forwarded-For`; the first local reuse attempt returned HTTP 400 `invalidClientAddress` for that test-only configuration mistake. After correcting the disposable fixture, reconciliation succeeded **2/2** with **10/10** successful requests, and reuse completed **2/2** 3v3 victories with **84/84** successful requests and **zero new players**. Later isolated increments from pool size 2→3 and 3→4 added exactly one account each (71/71 and 37/37 successful requests). The final disposable database had integrity `ok`, four players, four occupied slots and zero active leases; the loopback server, Recovery-Code pool, SQLite database, key and certificate were then removed.
