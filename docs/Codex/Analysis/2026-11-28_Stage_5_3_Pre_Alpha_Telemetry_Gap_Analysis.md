## Executive finding

RELEASE-004 has durable Public identity, save ownership, battle leases, diagnostics, terminal settlement and stage/Arena progression. It **does not have a player telemetry system**: there is no durable visitor attribution, 30-minute engagement session, immutable battle roster/formation snapshot, feedback intake, client-error reporting, or restricted analytics export. Existing diagnostic rows can support limited historical player/battle counts, but cannot reconstruct visitors, team diversity/switches, exact first-battle funnel, or a complete technical-error denominator. The P0 work therefore needs new capture from launch forward; old data must be labelled partial, not backfilled by inference.

Effort below is rough **engineering days** for a focused implementation, excluding Owner/privacy-policy decisions and a scheduled deployment window. Rows overlap; they are not additive. “Partial” means some relevant raw data exists, not that the requirement or KPI is already met.

For scheduling, the overlapping P0 rows suggest roughly **12–18 engineering days for Batch B** plus **3–5 days for Batch C validation/release preparation**, subject to the migration/rollback proof and privacy decisions. This is a planning range, not an approved commitment.

## Twelve core KPI feasibility

| KPI | RELEASE-004 historical data | Prospective P0 source and guard |
|---|---|---|
| 1. Unique Visitors | **No** browser-level identifier or first-visit events. | Distinct first-party visitor IDs; estimate browsers, not people. |
| 2. New Players | **Yes, raw count** from `players.created_at`, but existing test/bot exclusion is not encoded. | Server enrollment event and explicit internal-test flag; recovered sessions are not new players. |
| 3. First Battle Start Rate | **Not exact.** Reservation rows can precede failed activation; visitors denominator absent. | Activated battle start divided by eligible new visitors/players per published definition. |
| 4. First Battle Completion Rate | **Partial.** Terminal outcomes exist, but start cohort is approximate and outcome/error semantics need audit. | Activated first battle with one canonical terminal record; explicit denominator/window. |
| 5. Second Battle Start Rate | **Approximate for identified players only** from diagnostic ordering, not exact activation or window. | Canonical activated second battle by player, with seven-day activation window. |
| 6. Average Battles per Player (and median) | **Approximate** from reserved diagnostics; no internal-test exclusion. | Count activated starts per eligible player; report mean and median, observation window. |
| 7. Retry After Defeat Rate | **Partial/inexact.** Outcomes and stage context exist, but durable attempt identity, exact activation and encounter-specific ordering are incomplete. | Next battle start for same player+mode+encounter after defeat; distinguish changed team separately. |
| 8. Composition Diversity | **No.** Historical roster snapshots absent. | Unordered hero-ID multiset at launch; preserve slot arrangement separately. |
| 9. Team Switching Rate | **No.** Historical adjacent team pairs absent. | Compare adjacent same-player+mode activated battles; report formation-only change separately. |
| 10. D1 Retention | **Not exact.** Battle timestamps are sparse engagement proxies; no meaningful sessions. | UTC cohort at first meaningful play, return on next UTC day; mature cohorts only. |
| 11. D7 Retention | **Not exact** for the same reason. | Return on seventh UTC day; do not use immature cohorts. |
| 12. Technical Error Rate | **No complete denominator/numerator.** Battle terminal reason is not all API/JS/engine errors. | Publish request-level definition and separate battle-failure/JS rates; sanitized count, latency and error-category capture. |

Historical reporting should be explicitly labelled “RELEASE-004 diagnostic baseline, partial.” No migration can recover uncaptured visitors, roster selections, engagement or client errors. Derived P0 KPIs should start at the telemetry cutover and state observation windows, exclusions and N/A denominators. The specification's D1/D7 group is treated as two KPIs to make twelve.

## P0 design recommendation

1. **Reuse authoritative writes.** The Public enrollment and battle lifecycle transactions already know identity, active slot, server-resolved enemy, outcome and reason. Record only additive immutable facts there; make battle-start authoritative at activation, not reservation, and terminal events idempotent with existing settlement. A narrow roster snapshot table keyed by battle ID, or bounded additive columns, should store both ordered teams, formations, available roster, stage/mode/attempt and build/ruleset version. Do not dry-run combat or write React-derived battle results.
2. **A small validated first-party event boundary.** A same-origin endpoint accepts only allowlisted low-volume browser facts (`landing_view`, `home_view`, throttled meaningful activity/session and sanitized `client_error`) with schema-versioned event UUID, nullable visitor/player/session IDs, server receipt timestamp, environment/build, and bounded payload. Authenticated writes use existing Origin/CSRF/session rules; anonymous ingestion needs its own tight rate/body/origin policy. Use server-held stable player ID and first-party random visitor ID; no fingerprint. It is acceptable for frontend delivery to be best-effort if dropped counts are observed and gameplay never waits for analytics.
3. **Separate logical events from storage duplication.** A normalized export can project `identity_created`, `battle_started`, `battle_ended` and `battle_abandoned` from canonical rows while client-only facts live in a compact events table. If physical event rows are required, insert them in the *same* transaction as canonical mutations with uniqueness constraints; never maintain two independently committed battle truths. Materialized event IDs must be stable UUIDs, and duplicate/reordered client submissions must be idempotent.
4. **Meaningful sessions and source.** Start a 30-minute analytics session from qualifying activity; throttle activity and terminate by inactivity, not browser-close. Preserve allowlisted first-touch source and session source. `player_sessions` remain authentication credentials, not analytics sessions. UTC definitions and explicit test-account flags are required for valid cohorts.
5. **Feedback and operations.** Implement a small optional post-first-battle/menu flow and secured feedback endpoint. For request reliability, prefer sanitized route-template/status/latency aggregates or bounded structured logs, not a SQLite write on every API call. Add monitored host CPU/RAM, SQLite busy/errors, dropped telemetry, and current battle lease samples; show sources separately in exports. Existing Nginx log capabilities must be verified during implementation, not assumed here. Keep one restricted, versioned snapshot export (CSV/SQL) for analysis; no dashboard or new service.

### Contract and privacy decisions for Batch B

Freeze names, allowed payload fields, status/outcome meanings, UTC session/cohort windows, test-account marking, event version and dedupe rules before implementation. `battle_abandoned` should be restricted to explicit quit or defined terminal timeout; server restart/lease expiry must remain separately reasoned unless Owner approves a grouping. “Technical Error Rate” needs a precise denominator (for example failed API requests / all API requests), with engine exception and JS-error rates reported separately rather than silently combined. The plan's proposed 90-day raw retention is a proposal, not an approved deployed policy. Obtain Owner/legal/privacy approval for notice, consent applicability, retention/deletion and restricted access before any Public collection.

## Migration, compatibility, capacity and rollback

- Public runtime intentionally refuses implicit schema migration (`battle_api/progression.py:266-304`). Schema v5 validation checks required tables/columns with subset semantics (`battle_api/progression.py:580-675`), so additive tables and nullable/defaulted columns may remain readable by RELEASE-004, but this **must be demonstrated on an isolated copy**, not assumed. Existing named-column inserts must remain valid. Bumping `schema_version` or `public_battle_schema_revision` would make RELEASE-004 reject the upgraded DB and threaten application rollback. Prefer a separate telemetry schema marker and a backup-first, explicit offline migration after a zero-active-battle preflight.
- Validate SQLite `integrity_check`/foreign keys and old/new application startup against protected migrated copies; preserve identity/recovery verifiers, slots, progress, Arena, leases and settlements. Test migration interruption, idempotent rerun, new-version failure, and reinstall of RELEASE-004 against migrated copy. If old-release compatibility cannot be proved, the Owner needs a different rollback plan before deployment; do not restore a stale pre-migration backup over live player progress.
- Telemetry volume is unknown until a pilot. Estimate storage using actual bounded event sizes and measured events/session, project 30/90-day database plus indexes, WAL and backup copies against the **last documented** ~2.3 GiB free after Stage 5.2 cleanup (`docs/Codex/Stage_5_2_Implementation_Report.md`). That figure is not a current Production measurement. Make disk headroom a deployment stop gate. Use composite indexes on player/time, session/time, battle, type/time; retention/deletion must consider FK and export behavior. Avoid per-request/event write amplification on the e2-micro and measure busy/lock time, p95 latency and dropped low-priority events at realistic concurrency.
- Telemetry failures must be isolated from gameplay, with explicit dropped/failure counters and no unbounded retry or credential exposure. Authoritative battle/identity writes should remain atomic; if the telemetry-dependent extension of a canonical write can fail, failure handling needs an explicit transactional policy rather than a silent half-record. Keep raw event queue bounded and short-lived.
- Current Single-Release strategy retains RELEASE-004 as a local archive/tag, not an inactive server installation (`docs/Technical/Public_Deployment_Runbook.md:3`). Rollback requires reinstalling the known release, preserving live DB and confirming schema compatibility. Backups currently reside on the same VM; accepted disaster-recovery limitations remain.

## Focused validation and deployment gates

Batch B local tests: first visit→enroll→home→first start/end→second start→D1/D7 fixture; win/loss/draw/resign/lease expiry/server restart; same-encounter retry and changed team/formation; slot/profile isolation; cross-device recovery; unavailable roster; duplicate/reordered events and terminal races; anonymous/session timeout; malformed/oversized/untrusted source; test-account exclusion; PII/secret redaction; optional feedback; telemetry outage without gameplay failure. Assert event ID uniqueness, UTC times, exact KPI denominators and zero historical backfill. Verify Development/Public route isolation and CSRF/Origin. Exercise migrated-copy old/new app compatibility, backups/restores, interrupted migration and rollback.

Batch C: integrated backend/frontend/typecheck/lint/build and controlled-count cohort/export tests; representative VM-like concurrency with baseline p50/p95, CPU/RAM, SQLite busy/WAL size and disk growth; client-error and dropped-event drills; privacy notice and restricted export access review. A release package and any Production preflight/deployment require separate Owner authorization. Before switch: current free-space/zero-lease check, protected DB backup and isolated migration rehearsal. After switch: health, existing account/save recovery and battle smoke, telemetry counts, export security, data preservation and backup freshness. Stop/rollback on gameplay, migration, privacy or disk regression; do not claim public launch on technical checks alone.
