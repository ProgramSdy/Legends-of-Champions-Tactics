# Stage 5.3 Batch B — local P0 telemetry implementation

**Status:** Implementation and independent review complete; Owner acceptance pending. This is a local-development deliverable, **not** a Production release, live migration, or authorization to collect Public telemetry. The authoritative 12-KPI definitions remain in the [Marketing telemetry plan](https://docs.google.com/document/d/1xcaV9ynYNIVsbWzD3NrUCZGcdsIi1JTwMUwdnf6LnlU).

## Delivered boundary

- Existing `players.created_at` owns identity creation; canonical `battle_diagnostics`/settlements own outcomes. An additive telemetry sidecar stores only first-party visitor/session observations and battle-launch facts absent from canonical records. Stage/Arena start facts are attempted **after** durable activation; terminal rounds are best-effort metadata. No gameplay transaction waits on or rolls back for telemetry.
- Public collection is off unless the backend explicitly has `BATTLE_API_ENABLE_PUBLIC_TELEMETRY=1`, a schema-revision-1 offline upgrade, and the client is built with `NEXT_PUBLIC_TELEMETRY_ENABLED=true`. Invalid enabled schema fails configuration preflight. The Development/Public battle/Engineering boundaries remain unchanged.
- The bounded browser contract accepts only allowlisted landing, home, meaningful activity and sanitized client error records. Analytics sessions use 30-minute inactivity, not authentication sessions. Duplicates, reordered landing, throttle/caps and Origin/session/CSRF checks are enforced. No raw URL, IP, recovery credential, token, stack, survey or feedback text is stored.
- HTTP request metrics are bounded in-memory route/status/latency aggregates with periodic and normal-shutdown best-effort flush. KPI reporting separates API, battle and client errors. Restricted offline KPI/battle CSV or SQL exports, exact-ID internal-account classification, and bounded telemetry-only 90-day provisional pruning are provided in `battle_api.telemetry_ops`; operator UID allowlisting, private output and `--execute` are required. No public analytics/export endpoint exists.
- The existing Game Manual menu, accessible from Stage Map and Battle, has a Feedback & Bug Report link only when a configured credential-free HTTPS URL exists. It opens in a new tab with `noopener noreferrer`; no in-game feedback flow is added.

## Residual risks and Batch C/launch gates

- A hard process kill can lose an unflushed request-metric batch or a post-commit sidecar write; completeness/drop rates must be measured. A normal shutdown uses the bounded flush. Histogram latency is bounded, not a full per-request log.
- API error rate is service-wide and includes internal traffic; player/session/battle cohorts exclude only exact classified internal IDs. The Owner has not yet supplied final Production internal IDs. No historical visitor/session/roster facts are fabricated or backfilled.
- The 90-day raw retention is provisional. Final privacy notice/consent, retention policy, named operators, external feedback URL and performance acceptance thresholds remain Owner/Stage 6 gates. Restricted operator invocation needs a host access/audit procedure before Public use. Public capture remains disabled.
- This Batch B closeout used automated browser-component and API tests, not a manual end-to-end browser session with both telemetry gates enabled. A representative interactive browser flow and storage/latency observation remain Batch C validation work; no manual success is claimed here.
- Batch C may propose a **maximum 20% P95 latency regression** against a comparable Stage 4 30-player baseline, subject to final Owner approval.
