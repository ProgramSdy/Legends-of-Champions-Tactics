## Proposed event and database contract

Do not add another player or outcome store. `players.created_at` supplies new identity; existing `battle_diagnostics`/`battle_settlements` supply terminal outcome/reason. A new `telemetry_battles` sidecar, keyed by `battle_id`, supplies only absent immutable activation and roster/formation/availability/round facts. `telemetry_visitors` holds first-touch source; `telemetry_sessions` holds meaningful 30-minute analytics sessions; `telemetry_events` contains allowlisted low-volume browser observations; `telemetry_internal_accounts` excludes exact player IDs from public cohorts. All event records use UUID IDs, schema version, server-receipt UTC, nullable stable visitor/player/session/battle IDs, producer, environment/build and validated bounded data. Browser time is optional metadata, never the authoritative cohort clock. Stable hero/encounter IDs, not labels, are required. Duplicate client event IDs are idempotent; repeated battle IDs never create a second start/terminal. `feedback_submitted` is removed from the contract.

Capture only after successful canonical commit or derive directly from canonical records. A telemetry insert/update that fails, times out or is dropped **cannot fail or roll back** enrollment, battle activation/settlement, reward grant or save. No telemetry call waits inside the critical transaction. A bounded post-commit sidecar attempt has short timeout and no unbounded retry; a sanitized drop counter and completeness report expose gaps. Canonical terminal state remains unique and authoritative even when the sidecar is absent. Reconcile only facts that exist in canonical records; never fabricate missing visitors, rosters or sessions. This explicit availability/completeness tradeoff is tested before launch.

No event collection in Public until the default-off gate is deliberately enabled after privacy and launch requirements are met. Analytics sessions are not `player_sessions`; auth touch does not count as engagement. Internal account classification uses exact reviewed Player IDs, not names. Source values are allowlisted; raw URLs, IPs, Recovery Codes, cookies, CSRF tokens, arbitrary text and precise location stay out of event payloads and exports.

## Focused validation and release/rollback acceptance

Batch B tests: activation versus provisional reservation; first/second/retry exact windows and same encounter; UTC D1/D7 day edges and immature cohorts; composition versus slot/formation changes; win/defeat/draw/resign/expiry/restart/error distinction; owned roster/available heroes; cross-device recovery; duplicate/reordered event/terminal calls; anonymous visitor and source allowlist; inactivity boundary; exact internal-account exclusion; errors and latency denominators; malicious/oversized input; telemetry outage during identity, battle settlement, rewards and saves; restricted export, retention and redaction. Test no historical backfill and N/A denominators.

Batch C gate: integrated backend/frontend/typecheck/lint/Development and Public builds; offline migration on protected copies; new code and **unmodified RELEASE-004** opening/using the migrated copy, with integrity/foreign keys and player/save/settlement fingerprints unchanged; interrupted migration/retry; backup/restore and actual Single-Release reinstall procedure without overwriting live progress. Compare bounded telemetry-enabled 10/20/30-player, 3-RPS Stage 4 scenarios where separately authorized, recording p50/p95, 30-lease participation, settlement completeness, CPU/RAM, SQLite busy, WAL, disk and drop counts. The prior final 30-player sample achieved 30/30 settled, 2.97 battle RPS and ~1,090 ms battle-request P95, but was not a 300-second endurance proof. Propose at most 20% P95 regression under comparable conditions, subject to final Owner approval; stop thresholds must still account for pilot variance before launch.

Storage planning uses a strict event/row cap and 90-day provisional raw retention. The Technical architecture gives 100/500 daily-player scenarios; real bytes/row, WAL, indexes and backups must be measured on disposable data and checked against **current** Production headroom at a separately authorized preflight. Delete telemetry rows incrementally by UTC cutoff without touching canonical player, save or battle records. Exports are operator-only protected snapshots and omit secrets. Privacy notice, final retention/deletion policy, external feedback destination and launch authorization remain gates; code deployed with capture disabled is not a successful Public telemetry launch.
